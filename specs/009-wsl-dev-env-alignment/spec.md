## Clarifications

### Session 2026-05-16

- **Policy (general)**: For any similar future question about how to treat a file or directory that is generated by `specify init` / a vendor-managed install step, the project adopts the following rule, articulated by the user during this session: **if the artifact is dev-environment-only (only project maintainers run it), the project standardizes on bash (`sh`) and drops the PowerShell flavor entirely; if the artifact is user-facing (end users invoke it via shipped slash commands or extensions), the project makes flavor-compat seamless and automatic — typically by treating the install-generated form as developer-local state (gitignored, regenerated by `specify init --here --script <flavor>`), so each developer's chosen flavor Just Works without the repo committing both copies.** This Policy generalizes the answers to Q1 and Q2 below and is binding on any similar artifact discovered during `/speckit-plan` (e.g., `.specify/integrations/*.manifest.json` and analogous install-time configuration files).
- Q1: For `.specify/scripts/`, should the repository commit both `.ps1` and `.sh` flavors, or treat the directory as install-time-generated state that each developer regenerates via `specify init --here --script <flavor>` after clone? → A: **Option B** — `.specify/scripts/` is install-time state. Add it to `.gitignore` (extending the v0.4.2 precedent that already gitignores `.specify/workflows/...`, `.specify/extensions/.registry`, `.specify/extensions/.cache/`). Each developer runs `specify init --here --script <their-flavor>` once after clone as a documented one-step bootstrap in `AGENTS.md`. The repository does NOT bind itself to any single shell flavor.
- Q2: The vendor-managed `.claude/skills/speckit-{analyze,checklist,clarify,implement,plan,tasks,taskstoissues}/SKILL.md` and the equivalent `.agents/skills/speckit-*` files hardcode `.specify/scripts/powershell/check-prerequisites.ps1` paths and are regenerated by `specify init` against the chosen flavor — should they also be treated as install-time state per Q1's logic? → A: **Option A** — yes, extend the gitignore to these vendor-managed install-state files. Explicit exception: `.claude/skills/speckit-superpowers-bridge/` and `.agents/skills/speckit-superpowers-bridge/` are the project's own deliverable (CLAUDE.md declares them as the home of "custom bridge behavior") and MUST stay committed. A single `specify init --here --script <flavor>` regenerates both `.specify/scripts/` and the vendor-managed skill files in lockstep — no scripts/skills flavor drift is possible.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Maintainer can run the full bridge toolchain from WSL bash (Priority: P1)

A maintainer who previously developed this Spec Kit extension from Windows PowerShell has moved their working copy to WSL (Ubuntu, accessed under `/mnt/c/...`). They open a new WSL bash shell at the repo root and need every routine command they used on Windows — running the bridge runtime scripts, executing the smoke-test suite, invoking `/speckit-*` slash commands, opening PRs with `gh` — to work without falling back to Windows or hitting "command not found" / "script flavor missing" surprises.

**Why this priority**: This is the entire point of the migration. Without P1 the maintainer literally cannot complete a routine release/PR cycle from their new primary environment, and is forced to context-switch back to Windows for every iteration.

**Independent Test**: From a fresh WSL bash shell at the repo root, the maintainer (a) runs the project's smoke-test command, (b) runs one end-to-end slash command that exercises the bridge runtime (`/speckit-specify` → branch creation → spec file land), and (c) opens a draft PR via `gh`. All three succeed without manual workarounds, missing-tool errors, or CRLF/path-translation diagnostics.

**Acceptance Scenarios**:

1. **Given** a fresh WSL bash shell at the repo root, **When** the maintainer runs the project's smoke-test entrypoint, **Then** every test in `tests/` either runs and passes, or is explicitly and deliberately skipped with a one-line reason — not silently absent.
2. **Given** the same shell, **When** the maintainer invokes the bridge-state helper used by `update-handoff` and `guard-command`, **Then** the helper prints the `[bridge state]` summary block with the same fields and values it prints under Windows PowerShell.
3. **Given** the same shell, **When** the maintainer runs `/speckit-specify` with a short description, **Then** the configured `before_specify` hook executes a flavor of `create-new-feature` that is present on this host, a new branch is created, and the spec scaffold lands — without the maintainer first having to swap script flavors by hand.
4. **Given** the same shell, **When** the maintainer runs `gh pr create` against a fork, **Then** the command completes without proxy / DNS / auth surprises specific to WSL.

### User Story 2 - Repo working tree is clean after a fresh WSL clone (Priority: P1)

A second developer (or the same maintainer on a fresh machine) clones the repo into WSL for the first time. After `git clone`, `git status` shows a clean working tree. Bash scripts under `.specify/extensions/.../scripts/bash/` are executable. PowerShell scripts under `.../scripts/powershell/` keep their CRLF line endings as the project's `.gitattributes` already declares. No file in the repo silently flips line endings the next time anyone runs `git status` on either WSL or Windows.

**Why this priority**: Without P2 every WSL clone immediately shows ~80 phantom-modified files (the current 81+/81− `.gitattributes` / `.gitignore` working-tree diff is exactly this pathology), poisoning every subsequent `git status`, `git diff`, and PR diff with noise that hides real changes. P1 and P2 are equally load-bearing for "the WSL dev box is usable".

**Independent Test**: On a fresh WSL clone, run `git status` immediately after clone — it MUST report "nothing to commit, working tree clean". Touch nothing, then run `git status` again from a Windows PowerShell on the same machine pointed at the same checkout — it MUST also be clean.

**Acceptance Scenarios**:

1. **Given** a fresh `git clone` into a WSL filesystem path, **When** the developer runs `git status` with no edits, **Then** the working tree is reported clean.
2. **Given** a fresh `git clone` into `/mnt/c/...` (Windows-drive-backed WSL), **When** the developer runs `git status` with no edits, **Then** the working tree is reported clean.
3. **Given** any bash script under `.specify/extensions/.../scripts/bash/`, **When** the developer runs it directly, **Then** the script's shebang resolves and the script executes — no "bad interpreter: ^M" / CRLF errors.
4. **Given** the currently-uncommitted `.gitattributes` / `.gitignore` working-tree diff, **When** the alignment is complete, **Then** that diff has either been committed (because the normalization is correct and intended) or reverted (because it was a tooling artifact) — it is NOT left dangling.

---

### User Story 3 - Onboarding note for the next WSL developer (Priority: P2)

A future contributor reads the agent context file (`AGENTS.md`, which the project's `CLAUDE.md` declares as the master) and sees a short, scannable section telling them what the supported host environments are, which prerequisite tools they need installed for each, and which script flavor each environment uses. They do NOT have to reverse-engineer this from `init-options.json` or the extension directory tree.

**Why this priority**: Without P3 the alignment is one-developer-deep and erodes the next time someone joins. With P3 the migration's lessons are captured in the same file every coding agent and human contributor already reads first.

**Independent Test**: A reader who has never touched this repo opens `AGENTS.md`, finds an "Environments" (or equivalent) section in under 30 seconds, and from that section alone can answer: "What do I need installed in WSL to run the test suite?" and "Which script flavor does this project use on which host?".

**Acceptance Scenarios**:

1. **Given** the maintainer file `AGENTS.md`, **When** a new contributor reads it top-to-bottom, **Then** they encounter an explicit "supported host environments" statement that names at minimum Windows PowerShell and WSL bash, and lists each environment's required prerequisite tools.
2. **Given** that section, **When** the contributor compares it against `.specify/init-options.json`, **Then** the two are consistent — the documented default script flavor matches the configured `script` field, with any deliberate divergence called out explicitly.

### Edge Cases

- The checkout lives on the Windows drive (`/mnt/c/...`) rather than the WSL native filesystem (`~/...`). Permissions, line endings, and file-watcher behavior all differ. The alignment MUST work in the `/mnt/c/...` location because that is where the maintainer's checkout currently lives.
- A maintainer alternates between WSL bash and Windows PowerShell on the SAME checkout. The repo MUST NOT produce phantom `git status` noise when the host switches.
- A required tool (`gh`, `jq`, the chosen shell flavor) is missing on the WSL host. The alignment MUST make this fail loudly and early with a clear "install this" message, rather than silently producing wrong output.
- The `before_specify` / `before_plan` / `before_tasks` hooks in `.specify/extensions.yml` invoke a script flavor that is not present on the host (e.g., they invoke a PowerShell flavor on a host with no `pwsh`). The alignment MUST resolve this — either by ensuring the configured flavor IS present, or by ensuring the hook resolves to a flavor that is present.
- A bash script in `tests/` or `.specify/.../scripts/bash/` is checked out with CRLF line endings (because Windows-side autocrlf converted it). The bash interpreter will reject it. The alignment MUST prevent this.
- WSL is behind a corporate HTTP proxy that the Windows side handles transparently but the Linux side does not. The maintainer's `gh` and any outbound HTTPS the bridge makes MUST work, or the alignment MUST document the proxy step.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The repo's `.gitattributes` rules MUST classify every committed text file (shell scripts, PowerShell scripts, Markdown, JSON, YAML, and any other text format the project ships) such that a fresh `git clone` produces a clean `git status` on both WSL bash and Windows PowerShell, without requiring any developer-side `core.autocrlf` setting.
- **FR-002**: The currently-uncommitted `.gitattributes` / `.gitignore` working-tree changes (a 1-to-1 81+/81− line swap that is verified to be pure CRLF→LF line-ending normalization, with no semantic difference) MUST be resolved by **committing the LF-normalized form** with a one-line rationale ("normalize CRLF→LF in line-ending policy files for WSL parity"). Reverting is rejected because (a) `.gitattributes` itself declares `*.sh text eol=lf`, so keeping its own bytes in CRLF was internally inconsistent, and (b) any future WSL touch would re-produce the same diff. After commit, `git status` MUST report a clean working tree on both WSL bash and Windows PowerShell with no developer-side `core.autocrlf` configuration.
- **FR-003**: A maintainer on WSL bash MUST be able to execute every bash-flavor script under `.specify/extensions/.../scripts/bash/` directly (`./script.sh`) without first running `dos2unix` or `chmod +x` by hand on a fresh checkout.
- **FR-004**: The project MUST classify each script directory as either **user-facing** (invoked by end users via shipped slash commands, or by the bundled extension scripts) or **dev-internal** (invoked only by the project's own maintainers, e.g., the smoke-test harness). The classification follows the rule established by the user during clarification: **user-facing scripts whose presence is `specify init`-generated MUST be treated as install-time state (gitignored, regenerated per developer per Clarifications Q1); dev-internal `.ps1` scripts MUST be ported to `.sh` and the originals deleted**. This rule binds FR-005, FR-006, FR-007 below.
- **FR-004a (classification)**: `.specify/scripts/` is user-facing AND install-time-generated by `specify init --here --script <flavor>`. `.specify/extensions/.../scripts/{bash,powershell}/` is user-facing AND part of the project's own shipped extension package (NOT install-generated by Spec Kit). `tests/*.ps1` is dev-internal (callers are only docs, specs, and maintainer-run smoke tests — no runtime script invokes them).
- **FR-005**: `.specify/scripts/` MUST be added to `.gitignore` and untracked from the index (the existing `powershell/` flavor MUST be removed via `git rm -r --cached .specify/scripts/`). `.specify/init-options.json`'s `script` field MUST be set to `"sh"` to reflect the WSL maintainer's chosen default; on a fresh clone the developer regenerates `.specify/scripts/` by running `specify init --here --script <flavor>`. The project's own packaged extensions under `.specify/extensions/.../scripts/{bash,powershell}/` are NOT affected by this rule — they remain committed in both flavors because they are part of the release `.zip` and not generated by `specify init`.
- **FR-005a (bootstrap)**: `AGENTS.md` MUST document a one-line bootstrap step ("after `git clone`, run `specify init --here --script sh` (or `--script ps`)") in the supported-environments section (FR-010), so that a new developer can recover the gitignored `.specify/scripts/` directory in a single command.
- **FR-005b (vendor-managed skills are install-state)**: Per Clarifications Q2, the vendor-managed slash-command skill files under `.claude/skills/speckit-{analyze,checklist,clarify,implement,plan,tasks,taskstoissues}/` and `.agents/skills/speckit-{same set}/` MUST also be added to `.gitignore` and untracked from the index (`git rm -r --cached`). The project-owned `.claude/skills/speckit-superpowers-bridge/` and `.agents/skills/speckit-superpowers-bridge/` directories MUST remain committed — they are the project's own deliverable per CLAUDE.md, not Spec-Kit-generated install state. The same one-line bootstrap from FR-005a regenerates these files in lockstep with `.specify/scripts/`.
- **FR-005c (Policy-driven future artifacts)**: Per the Policy in Clarifications, if `/speckit-plan` discovers additional `specify init`-generated files (e.g., `.specify/integrations/*.manifest.json`, future Spec-Kit-generated configuration), the plan MUST classify each as dev-environment-only or user-facing and apply the corresponding rule (drop to `sh`-only for dev-env; gitignore + regen-on-bootstrap for user-facing) without surfacing it as a new clarification question.
- **FR-006**: The hooks declared in `.specify/extensions.yml` (`before_specify`, `before_plan`, `before_tasks`, `before_implement`, `before_checklist`, `before_analyze`, all `after_*`, etc.) MUST, on a WSL host with `init-options.json` set to `script=sh` AND after the FR-005a bootstrap has run, all resolve to a bash-flavor script that exists and is executable on this host. A maintainer MUST NOT have to hand-edit hook commands to switch flavors. (Resolution mechanism — typically `specify init` rewrites the vendor-managed slash-command files with the chosen flavor's paths — is implementation detail and will be settled in `/speckit-plan`.)
- **FR-007**: The `tests/*.ps1` files MUST be ported to bash equivalents (`tests/*.sh`) covering the same regression behavior — handoff shape (`test-handoff-shape`), guard hardcoded rules (`test-guard-hardcoded-rules`), bridge-state summary block (`test-bridge-state-summary`), and Claude/Codex skill parity (`test-claude-codex-skill-parity`). After porting and proving green on WSL bash, the original `.ps1` files MUST be deleted. No `.ps1` test files MUST remain in the repo after this feature lands.
- **FR-008**: A maintainer running `/speckit-specify` from WSL bash MUST observe the `before_specify` hook executing and producing the same JSON output (`BRANCH_NAME`, `FEATURE_NUM`) and the same on-disk side effects (branch created, spec dir copied from template) as the Windows PowerShell equivalent — i.e., parity in observable outcome, not implementation.
- **FR-009**: A maintainer running the bridge runtime (`update-handoff`, `guard-command`) from WSL bash MUST observe the `[bridge state]` summary block printed with the same field names and value semantics as the Windows PowerShell flavor. This MUST be true regardless of which flavor is the documented default per FR-004.
- **FR-010**: The agent context file `AGENTS.md` (which the project's `CLAUDE.md` declares as master) MUST contain a short, explicit "supported host environments" section naming at minimum Windows PowerShell and WSL bash, listing each environment's required prerequisite tools (`git`, the chosen shell, `jq`, `gh`, and any others the FR-004 policy requires), and stating which script flavor each environment uses.
- **FR-011**: The supported-environments section in FR-010 MUST be consistent with `.specify/init-options.json` — any divergence between documented default flavor and configured flavor MUST be explicit and intentional, not a documentation drift.
- **FR-012**: The alignment MUST work for a checkout located under `/mnt/c/...` (Windows-drive-backed WSL filesystem), not only for a checkout cloned into the WSL native filesystem (`~/...`). The maintainer's current checkout lives at `/mnt/c/lihan_work/ai_workplace/codex_specify_superpower` and MUST keep working there.
- **FR-013**: The verification for this alignment MUST be **one full bridge end-to-end cycle from WSL bash** — `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → bridge handoff → `update-handoff complete` — with every hook firing and the `[bridge state]` summary block printing on every relevant step. The cycle MUST be captured as a committed evidence file (`specs/009-wsl-dev-env-alignment/verification.md` or equivalent), containing at minimum: the host environment (`uname -a`, bash version, `jq`/`gh`/`git` versions), the slash commands invoked in order, and the resulting state-summary blocks.
- **FR-014**: All changes made for this feature MUST be confined to (i) repo configuration files (`.gitattributes`, `.gitignore`, `.specify/init-options.json`), (ii) the agent context file `AGENTS.md` per FR-010 + FR-005a, (iii) the `tests/` directory (porting `.ps1` → `.sh` and deleting the originals per FR-007), (iv) untracking `.specify/scripts/` from the index per FR-005 and the vendor-managed `.claude/skills/speckit-{non-bridge}` / `.agents/skills/speckit-{non-bridge}` files per FR-005b, (v) `.specify/extensions.yml` only if hook resolution per FR-006 requires it, and (vi) the verification artifact under `specs/009-wsl-dev-env-alignment/`. No changes to the bridge runtime scripts (`update-handoff.{ps1,sh}`, `guard-command.{ps1,sh}`, `bridge-state.{ps1,sh}`) and no changes to the project-owned `.claude/skills/speckit-superpowers-bridge/` or `.agents/skills/speckit-superpowers-bridge/` skill files are permitted by this feature.
- **FR-015**: After the alignment is complete, the maintainer MUST be able to demonstrate, in a single short verification log committed under `specs/009-wsl-dev-env-alignment/`, that the FR-013 verification depth was met from WSL bash.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On a fresh WSL bash shell at the repo root, the project's smoke-test entrypoint completes in under 2 minutes with either all-pass or all-explicitly-skipped status — zero silently-missing tests, zero CRLF / "bad interpreter" errors.
- **SC-002**: On a fresh `git clone` into either a WSL native path or `/mnt/c/...`, `git status` reports a clean working tree on the very first invocation, with zero phantom-modified files. Switching shells (WSL bash ↔ Windows PowerShell) on the same checkout MUST NOT produce any new phantom-modified files.
- **SC-003**: The full bridge end-to-end cycle defined in FR-013 (`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → bridge handoff → `update-handoff complete`) completes successfully from WSL bash in a single session, with every hook firing, the `[bridge state]` summary block printing on every relevant step, and the resulting transcript committed under `specs/009-wsl-dev-env-alignment/`.
- **SC-004**: A new contributor who has never touched this repo can answer "What do I need installed in WSL to run the test suite?" by reading only `AGENTS.md` in under 30 seconds.
- **SC-005**: After the alignment lands, the number of `.gitattributes` / `.gitignore` lines reported as "modified" in `git status` on the maintainer's WSL checkout (with no other edits) is exactly zero.
- **SC-006**: Zero files under `.specify/extensions/.../scripts/bash/` and zero `*.sh` files anywhere in the repo have CRLF line endings after checkout in WSL.
- **SC-007**: The alignment introduces no new top-level directories, no new packaged extensions, no new bridge subcommands, and no new project-owned skill files — measured by `git diff --stat main..HEAD` after the work lands. Untracking `.specify/scripts/` from the index (per FR-005) and removing `tests/*.ps1` after porting to `.sh` (per FR-007) are explicitly in scope and expected to show as deletions; new `tests/*.sh` files inside the existing `tests/` directory are similarly expected.

## Assumptions

- The maintainer's current host is WSL2 (Ubuntu flavor, bash 5.2+) running atop Windows, with the repo checkout under `/mnt/c/...` and the Windows host still available as a secondary verification environment.
- `git`, `gh`, `jq`, and `python3` are already installed in the WSL environment (already verified — `gh` at `/usr/bin/gh`, `jq` and `python3` from a user Anaconda install). Per the FR-004 / FR-005 policy decision, `pwsh` is NOT required on the WSL host; the maintainer keeps a Windows machine for the rare case they need to run the legacy PowerShell flavor.
- The "Windows PowerShell" environment named in FR-010 means PowerShell 5.1+ on Windows (the project's documented baseline since v0.4.x), not legacy Windows PowerShell 2.0 / 3.0.
- The current `.gitattributes` already declares `*.sh text eol=lf` and `*.ps1 text eol=crlf`. The 81+/81− working-tree diff on `.gitattributes` / `.gitignore` was inspected (`git diff` shows every line identical except the trailing `\r`) and is verified as pure CRLF→LF normalization; FR-002 pins the resolution to "commit the LF-normalized form" without further question.
- The agent context file `AGENTS.md` is the right place to document host environments — `CLAUDE.md` already declares `AGENTS.md` as the master, and the supported-environments note belongs alongside the other cross-agent guidance.
- "Simple alignment" (per the user's wording "简单对齐") was clarified during specification to mean: keep both flavors where end users depend on them (the user-facing rule in FR-004), but collapse to bash where only maintainers run the scripts (the dev-internal rule in FR-004 — concretely, `tests/*.ps1` → `tests/*.sh` and the originals deleted per FR-007). The bridge runtime itself is NOT redesigned; no new abstractions are introduced.
- Corporate proxy handling on WSL is treated as an environment precondition the maintainer manages before alignment; the alignment documents the precondition rather than scripting it.
- The bash flavor of `.specify/scripts/` is NOT committed (per Clarifications Q1 = Option B). Each developer regenerates `.specify/scripts/` locally via the FR-005a bootstrap (`specify init --here --script <flavor>`); the repo's `.gitignore` excludes the directory so per-developer flavor choice produces no `git status` noise.
- The bash port of the four `tests/*.ps1` files keeps the same regression coverage but does NOT need to be bit-identical in implementation — the contract each test asserts (handoff shape, hardcoded guard rules, bridge-state summary, skill parity) is what the port must preserve.
- The verification artifact under `specs/009-wsl-dev-env-alignment/` is a short evidence log (terminal transcripts or a Markdown summary), not a new test harness; FR-013 governs its depth and contents.
